# 邀请返利运行规则

系统设置中的“邀请返利”和模块中心中的“邀请返利”共用 `referral_enabled` 配置。该开关控制新增邀请绑定、新增返利资格和用户入口；关闭后，已有待发返利仍会重试，退款冲回仍会继续。部署环境的 `REFERRAL_AVAILABLE` 控制模块是否可用；不可用时用户入口隐藏。

历史配置 `module.referral.enabled` 不再控制该模块，也不会覆盖显式关闭的 `referral_enabled`。已有 `referral_enabled=true` 的环境无需数据迁移；只设置过历史模块开关的环境，应在管理员页面确认并保存当前邀请返利开关。

用户布局通过 `GET /api/modules/user-status` 加载功能状态。该接口沿用公开模块状态的权限分类，仅返回 `referral` 和 `management_tokens`，每项包含 `name`、`available`、`enabled`、`active`，不返回管理员配置。请求失败时前端清除旧状态，隐藏相关入口；重新进入用户布局时刷新状态。

`GET /api/users/me/referral` 保持现有登录校验及本人数据查询行为。关闭开关会隐藏入口，已有邀请码和历史统计不会被删除。

## 不改表结构的持久化方案

付款规则快照复用 `payment_orders.gateway_response` 中的内部键 `_aether_referral_v1`；注册绑定与奖励义务复用已有邀请关系和奖励表。待冲回金额使用现有 `referral_rewards.pending_reversal_amount_usd`。本次不新增表、列、索引或数据库迁移。

规则在首次成功入账时锁定，快照与付款入账、首次付款标记和待发奖励一起提交。重复回调、管理员重试和后台对账按原有快照与奖励义务处理，不使用当前规则重算旧订单。旧订单没有可信规则快照时，不自动推定补发资格。

实际付款的充值与套餐购买参与返利；赠送、兑换码和管理员直接赠款不参与。首次实际付款独立于返利开关：关闭期间已完成首付，之后重新开启不会把第二笔付款当作首付；退款也不会重置首付资格。新付款遇到旧关系未记录首付时，只按已有真实入账事实识别首付身份，不推定旧奖励金额或补发旧奖励。

同一邀请关系只创建一次人头奖励义务；切换注册、邮箱验证或首付触发条件不会再创建第二份人头奖励。待发、失败奖励沿原有义务重试；管理员作废的义务不会因切换条件而自动重新创建。

注册类奖励先可靠保存发放义务，再尝试入账。邀请人钱包暂不可用时等待重试，不因入账失败删除已注册账户。选择邮箱验证人头奖励时，必须开启注册邮箱验证；不兼容的设置应被拒绝，系统不会自动替管理员开启邮箱验证。

## 退款审批与返利冲回

用户提交退款申请后进入待审批。管理员“处理退款”批准并占款，再“确认完成”退款；没有自动审批。调用支付网关退款前必须核实退款已进入处理中。

审批和完成操作前展示邀请人、应冲回返利、可扣赠款及预计不足金额。余额不足时，由管理员决定批准或拒绝退款；批准需要明确知晓不足提醒。金额变化时重新提示，不能沿用过期确认。

付款比例奖励和首付人头奖励按累计成功退款比例冲回；注册、邮箱验证人头奖励不因后续付款退款而冲回。例如订单奖励 $10，累计退款 40%，应累计冲回 $4。已冲回金额不重复扣除。

如果奖励尚未发放时订单已成功退款，补发会在同一事务内记录发放和冲回流水，钱包只增加净赠款，避免用户在两次操作之间消费应冲回的款项。金额目标按现有数据库的八位小数精度计算，最小单位的待冲回金额也会继续处理。

仅从邀请人的赠款余额扣回，不动充值本金、不生成负赠款余额。不足部分记录为待冲回，后续有赠款时继续处理。完成结果显示实际冲回与待冲回金额；暂时无法扣回的记录不能阻塞后续有可用余额的记录。

## 历史核查

`referral-history-audit.sql` 仅包含只读候选查询，供另行确认环境后核查历史无规则证据订单、受邀账户已删除的注册奖励和已记录待冲回款项。本次未连接数据库或执行该文件，因此没有生成真实业务数据报告。

候选记录不等于应补发或应扣款。应先核对当时开关、模式、费率和支付事实；证据不足交由管理员判断，不按今天的规则自动补钱或扣钱。

验收步骤：管理员在系统设置或模块中心开启邀请返利，普通用户刷新页面后应看到“我的邀请”，进入后显示邀请码、邀请链接和统计；关闭后刷新页面，入口应隐藏。确认普通用户加载状态时不请求 `/api/admin/modules/status`，并验证已有用户模块路由不再依赖管理员状态接口。

## 管理端邀请返利页面重构方案（2026-10-09，已实施）

本方案承接上述已确认的业务规则，让管理员先发现需要处理的返利，再追踪邀请关系、付款和退款。页面及只读接口已实现，本地验证见本节末尾。沿用现有配色、组件和管理权限，不新增表、列、索引或迁移，不改变返利计算及退款审批规则。

### 重构前页面的具体问题

- 邀请关系和返利记录上下堆叠，两套宽筛选栏占据主要空间；管理员进入页面后缺少明确的处理入口。
- 待冲回金额只藏在记录的“冲回”单元格内，没有全局汇总和专门筛选，难以发现余额不足产生的待处理款项。
- 返利表缺少邀请人、被邀请人和触发原因；仅凭类型、订单 ID 和金额无法追踪一笔奖励。
- 搜索框写“订单号”，当前接口实际查询 `source_order_id`；注册、邮箱验证奖励没有来源订单，也未说明原因。
- 当前“已发返利”汇总只统计 `applied` 状态的奖励原额，不能直接改名为“累计已发”。失败原因没有专门的持久字段，也不能拿管理员备注或更新时间冒充失败原因、失败时间。
- 当前已有真实分页和过期请求保护，重构应保留；加载失败需要页面内提示，不能让初始零值被误认为真实统计。

### 页面布局与默认工作入口

```text
邀请返利                          查看规则设置  刷新
页面顶部中间：总邀请 / 已首付邀请 / 已冲回 + 当前规则摘要
累计已发 | 待发金额 | 待冲回          三个主要金额
待处理 | 返利记录 | 邀请关系
待处理：发放失败选择卡 | 待冲回选择卡（各自显示数量）
当前列表标题行：标题 / 数量 + 人员选择 / 常用条件 + 查询 / 重置 / 刷新
全部记录可展开更多条件
当前标签的数据列表与独立分页
点击记录 → 右侧详情抽屉
```

默认进入“待处理”。通过两张选择卡切换“发放失败”和“待冲回款项”，一次展示一组列表，两组保留各自的筛选和页码。初次加载没有失败记录但有待冲回款项时自动选择待冲回；管理员手动选择后，后续刷新保留选择。失败记录提供重试发放、作废；待冲回记录提供详情和钱包、来源订单定位，并明确说明由系统继续收回。待发与处理中记录由系统继续重试，放在返利记录中查询。没有待处理项时显示明确的完成状态，并提供“查看全部返利”。

统计区域采用三个主要金额卡片与一行辅助统计；手机上累计已发占满一行，待发与待冲回并排。当前规则用一行只读摘要展示；标签栏、筛选区随宽度换行。全部返利默认展示人员、订单号、发放状态，关系 ID、类型、触发条件和冲回筛选由“更多条件”展开。桌面保留六列表格，将人员与奖励来源合并展示；窄屏使用记录卡片展示人员、金额、状态和操作。沿用现有主题、焦点样式和深色模式。

规则摘要只读，修改统一进入现有系统设置。功能关闭时提示“停止新增邀请和返利资格，已有待发及退款冲回继续处理”，仍允许管理员查看历史及处理原有义务。摘要展示当前规则；记录详情展示当时规则，两者不能混用。

| 区域 | 主要内容 | 交互 |
| --- | --- | --- |

| 待处理：待冲回 | 邀请人、来源订单、奖励原额、已冲回、待冲回金额 | 查看详情、定位钱包与关联退款；说明系统后续有赠款时继续处理 |
| 返利记录 | 人员、比例/人头类型、注册/邮箱验证/首付/付款触发条件、来源、金额、发放状态、冲回情况、时间 | 查询全部历史，独立筛选和分页，点击打开详情 |

来源为空时显示“注册奖励”或“邮箱验证奖励”，不显示无法解释的横杠。无历史快照时显示“历史规则未记录”，不套用当前费率；有快照时只返回需要展示的规则字段，不暴露完整支付网关响应或内部幂等数据。

发放状态与冲回情况分开展示：发放包括待发、处理中、失败、已发、作废；冲回包括无冲回、部分冲回、全部冲回和待冲回。待冲回由现有金额字段判断，是资金处理情况，不新增数据库状态，也不等同于待发。实际数据库 `reversed` 状态展示为“已发 / 全部冲回”。

统计均为后端全量汇总，明确标注“全部历史”，不受当前列表分页和筛选影响。已首付邀请仅表示有首次实际付款事实，不表示一定获得返利，也不因退款清零。累计已发采用已确认成功发放的金额事实，包含后来部分或全部冲回的奖励；已冲回单列，不作为累计已发的减项。保留原有统计字段兼容性，用管理端新字段表达新口径，避免改变用户端现有接口含义。

待发金额包含未完成发放的 pending、failed、applying 奖励；失败数量只统计 failed；待冲回金额和数量分别汇总现有 `pending_reversal_amount_usd > 0` 的记录。列表金额区明确区分原额、已冲回与待冲回，不把“原额减冲回”直接标成邀请人可用余额。默认金额可简洁展示，非零小额不得显示为零；详情提供最多八位小数，便于核对最小单位款项。

### 操作与退款衔接

- “补发”改为“重试发放”，只对 failed 显示。操作前展示对象、奖励原额及当时规则；已发生退款时说明只入账扣除应冲回后的净赠款。完成提示按服务端实际返回状态生成，仍失败、处理中或全额冲回不能统一提示“已补发”。
- 作废只允许 pending、failed，确认框说明“停止该奖励后续发放，同一邀请关系的人头奖励不会因切换规则重新生成”，填写操作原因，复用现有备注和审计能力。
- 行操作锁定具体奖励 ID，确认后不能因筛选、翻页或切换抽屉而提交另一条记录。等待期间防止同一操作重复提交；状态并发变化返回冲突时刷新记录，不显示成功。成功后刷新全局汇总与受影响列表，并保留筛选和正确页码。
- 待冲回记录说明赠款不足、系统后续继续扣回，仅赠款可扣，不扣充值本金。这里不提供本金扣款、负余额、手动清欠或“作废已发奖励”按钮。
- 退款审批继续在钱包页面完成，复用现有返利风险预览和确认组件。批准前展示邀请人可扣赠款及不足金额，由管理员决定；金额变化需要重新确认。待冲回记录通常对应已成功退款后的剩余款项，不能误显示为仍可拒绝的退款申请。
- 跳转钱包或退款详情需要同时实现目标页面定位能力。当前钱包页仅有标签路由读取，不能假设任意用户、订单、退款 ID 已支持自动定位；定位失败显示明确提示，保留复制 ID 的方式。

钱包定位复用订单、钱包详情，并补 `GET /api/admin/wallets/{wallet_id}/refunds/{refund_id}` 和 `GET /api/admin/wallets/{wallet_id}/transactions/{transaction_id}`。跨钱包目标返回 404。前端支持 `tab=orders&order_id=...`、`tab=refunds&wallet_id=...&refund_id=...`、`tab=ledger&wallet_id=...&transaction_id=...`；`tab=wallets&wallet_id=...` 在现有资金流水标签展示只读钱包卡。目标详情独立于全局列表分页，并明确说明下方仍为全局列表；链接打开不触发入账或退款批准。

管理员邀请返利入口始终保留，关闭或不可用时仍可查询历史；普通用户入口继续按功能状态隐藏。返利表和关系表在窗口宽度不足 1280px 时使用记录卡片，宽屏表格保留最小宽度和横向滚动，避免操作按钮变为单字竖排。

失败原因缺少持久证据时明确显示“未记录失败原因”，管理员备注单独展示；不新增错误存储表，也不虚构完整事件时间线。详情中的时间只对应已存在的业务事实。当前钱包赠款如需展示，须由后端实时查询并标为参考值，同一钱包多条奖励不可重复分配为独立可扣额度；审批时仍以既有风险预览为准。
